# Task prioritisation

Two sessions share this skill. Before the **stakeholder session**, **graduate** turns every open, assigned feedback row without an issue into one, grouping rows that share a theme, so each is investigated from the tracker. In the **team review** the team walks the table: every open issue and every issue completed in the last seven days, status reading Open, In progress or Complete and priority High, Medium or Low, each red, amber or green. The user edits priority, owner and the queue on the page and presses Save changes, which downloads one changes file, and **apply** writes it to the tracker.

The project declares its tracker and sheet in `docs/agents/task-prioritisation.json`. When that file does not exist, read [CONFIG-FORMAT.md](CONFIG-FORMAT.md), propose the file to the user from what the tracker and sheet hold, and write it once they agree. The scripts need a Python with `python-dotenv` and, for graduate, `openpyxl`, and run from the project root with `LINEAR_API_KEY` in the project's `.env`.

**On every run, check the queue rule.** If the project's `CLAUDE.md` does not name the config's `queue_label`, read [QUEUED-WORK.md](QUEUED-WORK.md), fill its section for this project, show it to the user and add it to `CLAUDE.md` only on their yes: the file is shared with the team, so it never changes unseen.

## Graduate

Graduate takes every open, assigned row of the feedback sheet that has no linked issue yet: a row with feedback, an owner, an empty issue cell and a status not in the config's `closed` list. A row with no owner stays on the sheet until someone is assigned. Each issue goes to its rows' owner. Whether a row is a data problem or a fix to build is decided later, when its issue is investigated, not here. Take the workbook's location from `docs/agents/issue-tracker.md`, and ask the user only when it is not there.

1. **Dry run.** Copy the workbook with the shell (`cp`) into `output_dir`, since a shared workbook is often open, and run `python <this skill>/scripts/graduate.py docs/agents/task-prioritisation.json <the copy> --dry-run`. It checks every lookup and prints each row it takes, with owner, priority and title. A `KeyError` names an owner or priority value the config's maps lack: agree its mapping with the user, add it and run again.
2. **Group.** Run `fetch_issues.py` (step 1 of Refresh) and match each row against the open issues, since a row is often already covered by an issue nobody linked. Then bucket the rest by the project's milestones (the `milestone` field in `issues.json`): rows on one milestone topic, such as prose, image selection, payment or the consultant screen, that one person could work through on one branch become one issue. Each new group needs one owner, so only rows with the same owner share one. Show the user both as one markdown table, written for someone who has never opened the sheet: one line per proposed issue, giving the existing issue's identifier, title and status or "New" with a proposed title, the milestone, the owner, the priority, a one-sentence summary of what the issue covers, and each of its rows by number with a plain summary of what that row reports (`Row 31: the deposit shows in the old currency after a currency change`). Mark how sure each match to an existing issue is. On their yes, write `output_dir/groups.json` as `{"new": [{"title": "Fix the checkout totals", "milestone": "3. Checkout", "rows": [12, 31]}], "existing": {"ENG-134": {"milestone": "3. Checkout", "rows": [22]}}}`: each `new` group becomes one issue with that title and milestone (`null` for none; a name the project lacks stops the run), and each `existing` entry links its rows to that issue without creating one. An existing issue already in progress is not widened: graduate makes a new issue for its rows in the entry's milestone, related to it, and links that instead. Rerun the dry run with `--groups <output_dir>/groups.json` and show the user the issues it would make. A `ValueError` names a group to fix.
3. **Graduate.** On the user's yes, ask them to close the workbook everywhere, then run the same command on the workbook itself without `--dry-run`. It creates the issues with the queue label, writes each address into its rows and reads the cells back. A `PermissionError` before any issue is made means someone still holds the file open. Report each issue made and each row linked.

## Refresh and apply

1. **Fetch every issue.** For a Linear project, run `python <this skill>/scripts/fetch_issues.py docs/agents/task-prioritisation.json`. It takes every issue of the config's `linear_project`, open or closed, and writes `issues.json` to `output_dir`. Another tracker needs its own fetch writing the same file: one JSON list of `{"id", "title", "status", "status_type", "completed_at", "assignee", "priority", "milestone", "labels"}`, `null` where there is no value, with Linear's status types (`triage`, `backlog`, `unstarted`, `started`, `completed`, `canceled`, `duplicate`). Done when it prints the count.
2. **Build the table.** Run `python <this skill>/scripts/build_table.py docs/agents/task-prioritisation.json <output_dir>/issues.json`. It keeps open issues and those completed in the last seven days, and drops cancelled and duplicate ones. A `KeyError` names a status or priority the config's maps lack: agree its mapping with the user, add it to the config and run again.
3. **Check and open.** Open `index.html` in `output_dir` and report both scripts' counts.
4. **Apply the review.** When the user says the review is done, take the newest `task-prioritisation-changes*.json` in their Downloads folder (ask where it is if it is not there). Each change names an issue by its `id`, the `field` and its `to` value, where an empty string means none.
   - Update each issue through the tracker: `priority` through the config's `tracker_priority`, `owner` as the assignee, and `queue` by adding the queue label for `"Yes"` or removing it for `"No"`.
   - Move the changes file into `output_dir`, so it is never applied twice, then rebuild the table (steps 1 to 3) and report each change applied. Done when every change in the file is reported as applied.

`output_dir` stays out of git: it holds generated copies of the tracker and the sheet.
