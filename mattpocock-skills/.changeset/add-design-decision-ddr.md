Add the `design-decision` skill and DDRs (design decision records), with the machinery that keeps them honest, and carry a rewritten `implement`, a tracker sweep and the rewind skills alongside.

- **`design-decision` and the register.** A DDR is one row in `docs/ddr/register.csv`, a filterable register, for a decision that fails the ADR test but would still be built wrong by an engineer who never heard the conversation: statused (proposed, in-research, accepted, rejected, deferred, superseded), tagged by layer, area, sub-area and project part, weighted by priority and risk, dated, and written before the edit that implements it. An undecided row names the tracker issue that settles it, and the issue names the row back. The register holds DDRs only. `domain-modeling` gains a "Route design rules to DDRs" section, a `DDR-FORMAT.md` beside `ADR-FORMAT.md` and the fixed area list in `taxonomy.json`; it now loads first in any project and reads the glossary and records before code. `grill-with-docs`, `triage` and `wayfinder` load `design-decision` beside `domain-modeling`.
- **Required ADR front matter.** An ADR carries `status`, `date`, `area`, `sub_area` and, where a part applies, `project_taxonomy`, the same tags a DDR row carries, so one filter reads both.
- **The records check and the sync hooks.** `domain-modeling/scripts/check_records.py` validates the register and the ADRs' front matter. The plugin's hooks run `sync_records.py`, which, in a project with `docs/agents/records.json` on `main`, keeps the records on `main` for every branch and runs the check before a record edit is pushed.
- **Fixed record places.** The glossary, ADR folder, register and tracker config sit at fixed defaults; `docs/agents/domain.md` names a record only when a project keeps it elsewhere. `setup-matt-pocock-skills` asks for the project taxonomy and writes `records.json`.
- **`implement` rewritten.** It carries a tracker issue, or the next free ticket in a scope (the frontier of a label, milestone or parent issue), to done: it loads `grilling`, `domain-modeling` and `design-decision`, explains the ticket and its binding records, asks every open point in one round, records each answer before building, and names a rewind point.
- **The tracker kept true.** `triage sweep` walks every open issue and proposes closing, merging or re-linking each, with evidence, applying only what the maintainer approves. The tracker templates gain a "Keeping the tracker true" section, and `to-tickets` checks the tickets already open before it publishes.
- **Decisions sections.** Tickets, specs and agent briefs list every binding ADR and DDR under a Decisions heading, or "None".
- **The rewind skills.** `prepare-rewind` writes `rewind-status.md` before the conversation is rewound to save tokens; `carry-on-rewind` reads it after the rewind, checks git, and carries on. Both are model-invoked, so the agent can write the handover while its context still has room.
- **`grill-with-docs` is model-invoked**, so the agent reaches for it when asked to grill a plan inside a repo, rather than only when the user types it.
